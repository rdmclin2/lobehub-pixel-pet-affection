# 分段式表达：一次回复拆成几条短消息，逐条上屏

你发一句话，她像真人发微信那样回：很多时候就回一句；有两三句想说就分两三条；好久没见或情绪上来时才连发四五条（比如“🥺”“在吗？”“有点想你了。”“在干什么呀？”）。桌宠窗口只有一个气泡，一次显示一条，下一条替换上一条；等下一条时当前这条后面跟着“正在输入”（三个跳动的点）。没看完也不用着急：点气泡就打开设置窗口的聊天页，整段回复都在聊天记录里。表情看心情，不是每次都有，也不固定在开头。语气更调皮、更亲近，但仍然只在当前关系阶段允许的范围里。

**核心是自然**：条数和表情都没有固定格式，下一节的两层机制只让回复的样子有变化，不强制分段。

只改**展示节奏**：用户提问 → 她回答的原有路径（聊天框、流式回复、朗读、聊天记录、梗图、插嘴、内容守卫、好感度）都不变，仍只按最终回复执行一次。

## 一、协议：每条消息独占一行，发几条每轮不同

- **人设**（`src/core/persona.js` `segmentRule`，系统角色第 12 条，`PERSONA_VERSION` 升到 10）：说明一条一行（用换行分开，不要空行、不要编号）、每条一般 ≤ 15 字、`prefs.segmentMax` 条封顶；一句就够就只发一条；表情看心情，放开头、中间、结尾或句尾都行，不要每次都用，更不要每次都拿表情开头。规则里有“现在几点 → 一条”“哈哈你真逗 → 一条带表情”“今天好累 → 两条”“隔了很久的嗨 → 四条且以表情开头”几个例子，并要求不要照抄、不要轮流套用。
- **节奏**（`persona.rhythmHint`，每条主人消息掷一次，写在 prompt 里主人的话前面）：只告诉模型“要有变化”时，真实 agent 12 轮全是 2–3 条，所以由代码来掷：

  | 情况 | 只回一条 | 2–3 条 | 连发 4–`min(segmentMax, 5)` 条 |
  | --- | --- | --- | --- |
  | 平时 | 60 % | 30 % | 10 % |
  | 主人离开 ≥ 6 小时 | 15 % | 25 % | 60 % |

  再掷一次表情：连发时 60 %（“其中一条可以只发一个表情”），其他 20 %（“带个表情”），否则“不用表情”。这是她这一刻想说多少话，不是格式要求：第 12 条规定不要提起它，办正事以把事说清楚为准。只有聊天消息有这一行，话题、主动搭话、事件没有。`分段式表达` 关掉时也没有。
- **离开多久**：`buildChatPrompt` 的 `lastSeenAt` 是这条消息算作互动之前的时间（`[状态]` 里的“距上次互动”同样用它；以前 `state.touch` 在拼 prompt 之前就把它改成“刚刚”，永远是 0 分钟）。
- **为什么是换行**：不需要新的分隔符，模型天然会写；只写一行时就是一条，不会露出奇怪的符号；聊天记录、设置窗口的聊天页、LobeHub 话题里看到的都是正常的多行文本。
- **人设更新**：`personaKey` 末尾多了 `seg<N>` / `noseg`，所以开关或改条数上限后，下一回合前她的 LobeHub agent 的 system role 会自动更新一次（`_ensurePersona`）。

## 二、切分：`src/core/segments.js`（纯函数，main / renderer / 测试共用）

| 函数 | 作用 |
| --- | --- |
| `split(text, { max })` | 最终回复 → 有序消息数组 |
| `plan(text, { final })` | 流式文本 → `{ segments, complete }`：已结束的行是 `complete` 条，最后一行可能还在写 |
| `typingMs(seg, i, { charMs }, rnd)` | 第 i 条出现前“正在输入”的时长 |
| `readMs(seg)` | 一条消息至少停留多久才能被下一条替换（桌宠窗口用，`hooks.holdMs`） |
| `createPlayer(hooks, opts)` | 播放调度器：一次只持有一个定时器，按顺序逐条交给渲染端 |

`split` 的规则（边界都有单测）：**她的换行是唯一的切分点**，这里不替她多拆。

1. 按换行切，去掉每行首尾空白和空行；`\r\n` 当作 `\n`。
2. **一行就是一条**：只有一行时不管多长都是一条，不按标点切。
3. **表情留在她放的位置**：单独一行就是单独一条（开头、中间、结尾都行）；写在一行里（`🥺 在吗？`、`好开心😊`）就留在这一行里，不拆出来。
4. **条数上限**：超过 `max`（`prefs.segmentMax`，默认 6）时，从第 `max` 条起并进最后一条（中文直接拼接，英文之间加空格）。
5. **整段保留**：含 ```` ``` ```` 代码块、两行以上 Markdown 列表 / 标题 / 表格、或全文超过 400 字的回复是“要读的答案”，不拆。

`plan` 用于流式：已经结束的行按上面的规则切（之后再来的文字不会改变它们），最后一行还在写；超过上限时被合并的那条一直保持“未完成”直到结束。单测逐字增长验证了已完成的消息不会变。

节奏 `typingMs`：第 1 条立即出现（之前已经“思考中…”过了）；纯表情约 420 ms；文字 `320 + 字数 × charMs`（`prefs.segmentCharMs`，默认 80 ms/字），夹在 0.5–2.4 s，再乘 0.8–1.2 的随机抖动，所以节奏不机械。例：`在吗？` ≈ 560 ms，`有点想你了。` ≈ 800 ms。

停留 `readMs`（只有桌宠窗口传给播放器；设置窗口聊天页的消息不会被替换，不需要）：纯表情 800 ms；文字 `700 + 字数 × 150` ms，夹在 1–4 s，不抖动。下一条的等待时间取“下一条的打字时间”和“这一条还需要停留的时间”中较大的那个，都从这一条出现时算起。例：`在吗？` 停 1150 ms，`有点想你了。` 停 1600 ms。

## 三、逐条上屏：渲染端（`src/renderer/app.js`「分段式表达」一节）

- **何时分段**：设置开着（`prefs.segmented`）、不是访客窗口、台词来自她自己（`source: 'llm'`，含聊天回复、话题、主动搭话、插嘴），并且切出来 ≥ 2 条。否则走原来的单气泡路径（包括单句回复、离线台词、错误、API 台词）。
- **样式：一个气泡，内容替换**：`#bubble` 还是普通的卡片和小尾巴，里面只有当前这一条（`.seg`），下一条出现时替换它，并带 0.22 s 的上浮淡入。等下一条时，“正在输入”（`.seg-typing`，三个跳动的点）跟在当前这条后面，这条不会消失。纯表情字号放大。`prefers-reduced-motion` 时不做动画。
- **点气泡看聊天记录**（`bindBubbleClick`）：点她的回复（`source: 'llm'`，分不分段都算，播放途中也可以）打开设置窗口的聊天页 `#/chat/<角色 id>`，桌宠窗口的气泡继续播放。鼠标移上去是手型，并提示“点击查看聊天记录”。“思考中…”、摸摸这类互动台词、错误和拖选文字都不触发；访客窗口也不触发。
- **流式**：`chat-delta` 照常到达。只有一行时仍是原来的“边写边显示 + 光标 ▍”；一出现第二行就切到分段播放：已结束的行排队，按她的节奏一条条出来（今天的 `lh` 在结束时一次性吐出全部文本，也照样逐条出现）；第一条如果还在写，就带光标实时显示；后面还在写的那条显示为“正在输入”，等这一行写完、打字时间够了、上一条也停留够了才替换上去（已经“打”过的时间会抵扣）。
- **最终台词**：`say`（带 `streamId`）给出权威的消息列表：工具前导语、梗图标签、守卫拒绝语都以它为准，当前这条不一致时原地改正；最终消息比已显示的少时退回最后一条；不会从头重放。
- **梗图贴纸**和**自动隐藏计时**（按最后一条的字数，屏上只剩它）等最后一条出现后才开始；**朗读**仍在最终台词到达时按全文读一次（逐句），气泡在读完前不会隐藏。
- **中断与衔接**（播放器只持有一个定时器，`cancel()` 清掉它）：
  - 你在她还没说完时发了新消息（`setThinking(true)`）→ 剩下的不再显示，立刻进入“思考中…”，新回复从第 1 条开始。聊天记录里旧回复是完整的。
  - Esc / 回合失败（`chat-done` ok=false）→ 已显示的留着，不再继续。
  - 新的流式回复、作曲中、语音唤起的“听你说”等占用气泡时 → 取消播放。
  - 摸摸 / 部位触摸 / 碎碎念这类“互动台词”（`IVoice.classify` tier 0、`source: 'fallback'`）在她还没说完时**不抢气泡**（记一条 `held`），和朗读的 `SpeechGate` 一样不打断回复；错误、API、新回复等其它台词照常接管气泡。
- **插嘴**：插嘴的那句如果分了段，「别插嘴 / 说得好」照常出现在气泡上方（判断条件仍是 `data-kind = interject`）。
- **e2e 钩子**：`window.petFx.segLog()`（每次 start / typing / reveal / update / truncate / cancel / done / held，带 `performance.now()` 时间戳）和 `window.petFx.segState()`（`{ id, total, complete, shown, live, typing, final, done, timer }`）。

## 四、聊天记录与其它环节的取舍

| 环节 | 行为 |
| --- | --- |
| 聊天记录（`chat-log.json`） | **保存完整原文一条**，消息之间是换行；不拆成多条记录。理由：一个回合仍是“一问一答”，好感度、话题、导出、`turnId` 配对和流式时的“实时行”都按一条回复设计，拆开会让这些都变复杂，而换行已经保留了分段信息 |
| 设置 → 聊天记录 | 只在显示时拆开（`admin/src/console/pages/replySegments.ts` `splitReply`）：她的回复一条一个气泡，时间和名字在第一条上，表情包、附件在最后一条下面 |
| 朗读 | 最终全文读一次（按句），不按条重复朗读 |
| 梗图 | `[梗图:id]` 标签照常由 `_say` 取出；贴纸在最后一条出现后显示 |
| 内容守卫 | 对累积全文检查，命中即撤回（分段播放同时被取消，显示 `……`） |
| 动作 / 意图 / 好感度 | 只按最终回复执行一次（主进程逻辑未改） |
| 设置窗口 → 聊天页 | 和桌宠窗口不同，这里是完整记录：一条一个气泡，每条都带她的头像；刚收到的回复用同一个播放器逐条出现，中间有“正在输入”（`usePacedReply`）；翻历史时直接显示全部。模型名、时间、表情包、音乐、错误在最后一条下面。长回答（代码、列表、超过 400 字）仍是一个气泡 |

## 五、配置项（`settings.json` → `prefs`，设置 → 玩法 → 桌宠行为 → 聊天）

| 键 | 默认 | 范围 | 说明 |
| --- | --- | --- | --- |
| `prefs.segmented` | `true` | 开 / 关 | 分段式表达总开关。关掉后整段回复一次显示，人设里的第 12 条也去掉（agent 自动更新） |
| `prefs.segmentMax` | `6` | 2–8 | 一次回复最多几条；同时写进人设（“N 条封顶”） |
| `prefs.segmentCharMs` | `80` | 30–200 毫秒/字 | 打字速度；越小越快 |

非法值回到默认值（`normalizePrefs`）；`set-prefs` 即时生效，渲染端下一条回复就按新值切分和计时。

## 六、如何触发

0. 启动：`npm install` → `npm start`（Linux 无显示器：`xvfb-run -a npm start`；不登录 LobeHub 先看效果：`npm run demo`，用假 `lh`）。分段式表达默认开启，不需要额外配置。
1. 正常唤醒她（任意角色），在聊天框随便发一句。每轮掷一次节奏，所以有时一条、有时几条，多发几句就能看到变化。想看连发（≥ 4 条）：隔 6 小时以上再发一句“嗨”，大约六成会连发；平时大约一成。
2. 不连 LobeHub、不花 token：跑下面的 e2e 场景，它用假 `lh`（`test/fixtures/fake-lh.js` 读 `$FAKE_LH_DIR/stream-reply.json`）回复固定的分段文本。注意只有她自己的回复（`source: 'llm'`）会分段，本机接口 `POST /pixel-pet/say` 的台词和离线台词不分段。
3. 想对比原来的样子：设置 → 桌宠行为 → 聊天 → 关掉「分段式表达」。
